# Методы криптографии и почему они выбраны

Пункт реестра Rent **MOD.crypto-rationale** (решение владельца 28.10-286 п. 1: по каждому методу — что выбрано, почему,
стандарты, отвергнутые альтернативы, когда пересматривать). Состояние на 13.11.2026.

**Источник фактов** — код Rent (HomenSAI/Homensai-Rent, ревизия `284efde3`), из которого модуль переносится пакетом MOD;
ссылки `файл:строка` даны по этой ревизии. Подпись лицензии — в ядре `homensai-platform` 4.47.0. Обоснования «почему» и
«альтернативы» взяты из комментариев кода и решений владельца (`docs/DECISIONS.md` Rent: 28.10-230, 269–279, 282, 284, 286);
то, чего в коде и решениях нет, помечено **«уточнить»**. Байтовые форматы — `spec/`, тест-вектора — `spec/vectors/`.

Библиотеки (свои примитивы не пишутся, AGENTS.md и 286): **pyca/cryptography 50.0.2** (OpenSSL 3 и Rust) — Argon2id,
X25519, Ed25519, ECDSA, RSA, HKDF, ChaCha20-Poly1305, AES-GCM, HMAC; **pyzipper 0.4.0** — WinZip AES в ZIP;
**pycryptodomex 3.24.1** — схема Шамира (её же использует pyzipper для AES); `hashlib`/`hmac` стандартной библиотеки — SHA-256,
HMAC-SHA256, сравнение за постоянное время, прежний scrypt.

## 1. Шифрование файла копии: ZIP AES-256 (WinZip AE-2)

**Что и где.** Внешний ZIP с одним членом `archive.zip` шифруется `pyzipper.AESZipFile(..., encryption=WZ_AES)` и
`setencryption(WZ_AES, nbits=256)` — `app/archive/pack.py:283-285`; служебный бэкап — `scripts/migrate.py:641-643`.
pyzipper без дополнительных аргументов пишет **AE-2** (CRC-32 = 0). Формат: PBKDF2-HMAC-SHA1, **1000 итераций** (зашито в
формате, pyzipper `zipfile_aes.py:201`), соль 16 байт, AES-256-CTR, HMAC-SHA1 (10 байт), проверочное значение 2 байта
(`spec/archive-format.md` § 2.1). Пароль ZIP:
- режимы `generated`/`custom`/`pin` (28.10-269/270) — случайный секрет копии, 32 байта из `secrets` в base64url
  (`app/archive/keys.py:51`, `:188`), запечатанный на ключ хозяйства (метод 3);
- режим `env` (прежний) — `BACKUP_PASSWORD` не короче 16 знаков без шаблонов (`scripts/migrate.py:295`, `:305-327`);
- режим `none` — без шифрования, только диски этого ПК (`app/archive/protection.py:5-9`).

**Почему.** Копия открывается обычным 7-Zip по паролю на любом ПК без программы (`app/archive/pack.py:2-7`); имена файлов с
фамилиями спрятаны во внутренний ZIP. AE-2 не пишет CRC открытого текста (CRC маленьких файлов выдаёт содержимое) и
проверяет целостность HMAC. Слабый PBKDF2 формата не важен при случайном 256-битном секрете (`app/archive/keys.py:8-9`);
в режиме `env` сила держится на длине пароля (`scripts/migrate.py:306-309`).

**Альтернативы.** ZipCrypto — сломан (атака по известному открытому тексту), не используется. AE-1 — пишет CRC. Формат 7z
(AES-256, SHA-256 2^19 раундов) — сильнее KDF, но нет проверенной библиотеки в зависимостях Rent — **уточнить** (в коде
не обсуждается). age/GPG как контейнер файла — требовали бы отдельной программы для восстановления вручную — **уточнить**
(в коде обоснован только выбор ZIP ради 7-Zip). Сам конверт ключа устроен «как age» (метод 3).

**Защищает от:** чтения копии на украденной флешке, в облаке, в Telegram; незаметной правки содержимого (HMAC AE-2 по
ключу из пароля); раскрытия имён файлов. **Не защищает от:** перебора слабого `BACKUP_PASSWORD` в режиме `env`
(1000 итераций SHA-1 дёшевы — поэтому ≥ 16 знаков); копий режима `none`; видимости метаданных внешнего ZIP (размер,
время, конверт); подмены комментария-конверта целиком (не покрыт HMAC — защищает AEAD конверта и подпись манифеста
цепочки, метод 9); утечки пароля с ПК. Заголовки ZIP (время, размер) не аутентифицированы.

**Пересмотр:** ежегодно; при росте вычислительных мощностей — поднять минимальную длину `BACKUP_PASSWORD`; вывод режима
`env` из употребления — **уточнить** у владельца.

**Миграция:** формат копии — `homensai-rent-archive/1`; старые копии читаются всегда (читатель смотрит комментарий).
Переход на другой контейнер — новая метка формата и новые вектора; прежние копии не перешифровываются (append-only,
28.10-279 п. 4) — их заменяет ротация.

## 2. Argon2id: пароли и PIN

**Что и где.**
| Применение | Параметры записи | Где |
|---|---|---|
| Пароль копий → ключ обёртки | `m=65536 КиБ (64 МиБ), t=3, p=4`, соль 16, ключ 32 | `app/archive/keys.py:48`, `:85-86`, `:115-119` |
| PIN копий (4 цифры) | `m=65536, t=8, p=4` | `app/archive/keys.py:49` |
| Пределы чтения из файла | `19456 ≤ m ≤ 1 ГиБ`, `2 ≤ t ≤ 32`, `1 ≤ p ≤ 16`, `m ≥ 8p` | `app/archive/keys.py:50`, `:70-82` |
| Пароль входа | те же 64 МиБ / 3 / 4, NFKC, соль 16, ключ 32 | `app/web/auth.py:41-45`, `:95-96`, `:156-176`; `migrations/webauth/0003_argon2id.sql:28` |
| PIN действий, запись PHC | 64 МиБ / 3 / 4, NFKC, PHC `$argon2id$v=19$…` | `app/security/kdf.py:24-27`, `:55-62`; `app/security/actions.py:68-69` |

**Почему.** Решение 28.10-279 п. 3: Argon2id вместо scrypt, параметры не слабее OWASP (минимум `m=19 МиБ, t=2, p=1`,
`app/security/kdf.py:4-5`, `:25`). Argon2id — победитель Password Hashing Competition, RFC 9106, первый выбор OWASP; память
дорожит перебор на GPU/ASIC. PIN: 10 000 вариантов перебираются быстрее любого пароля, поэтому каждая попытка дороже
(`app/archive/keys.py:46-47`) — и всё равно копии с PIN только на дисках этого ПК с постоянным предупреждением (269).
Параметры лежат рядом с хэшем — их можно усилить позже (`app/security/kdf.py:6-7`).

**Альтернативы.** scrypt — прежний метод (до 279), читается и перешифровывается (`app/web/auth.py:7-9`, `:37-40`);
PBKDF2 — без затрат памяти, OWASP требует 600 000 итераций SHA-256 — **уточнить** (в коде сравнения нет); bcrypt —
предел 72 байта и 4 КиБ памяти — **уточнить** (в коде не обсуждается).

**Защищает от:** перебора пароля по украденной копии, конверту, базе; подложенных параметров, требующих гигабайты памяти
(верхние пределы). **Не защищает от:** слабого пароля (поэтому правила силы: копии — `protection.password_problem`,
вход — от 10 знаков и список утёкших, `app/web/auth.py:140-149`); PIN — от перебора по копии (10 000 × ~0,5 с — **уточнить**
замер на целевых ПК); кейлоггера.

**Уточнить:** пароль копий кодируется UTF-8 без NFKC (`app/archive/keys.py:117`, `:129`), пароль входа и PIN — с NFKC
(`app/web/auth.py:95-96`, `app/security/kdf.py:55-56`): один и тот же пароль, набранный в другой раскладке/форме
Unicode, для копий не совпадёт.

**Пересмотр:** ежегодно и при новой редакции OWASP / NIST SP 800-63B / RFC 9106-бис; поднять `m`/`t`, если проверка на
целевом ПК занимает < 0,5 с — **уточнить** целевое время.

**Миграция:** вход и PHC — `needs_rehash` и перешифровка при следующем успешном вводе (`app/web/auth.py:186-196`,
`app/security/kdf.py:86-92`). Ключ копий: параметры в `wrapped`, новые копии берут текущие; усиление прежнего `wrapped`
происходит при смене пароля (новая пара, `app/archive/runner.py:227`) или при сбросе ключом восстановления
(`app/archive/recovery.py:170`, `:201`); автоматической перезаписи `wrapped` при успешной проверке пароля нет — **уточнить**,
нужна ли.

## 3. Ключ хозяйства: X25519 + HKDF-SHA256 + ChaCha20-Poly1305

**Что и где.** Пара X25519 хозяйства; закрытый ключ — под паролем (метод 2) ChaCha20-Poly1305 (`app/archive/keys.py:110-120`).
Каждая копия — новый секрет, запечатанный на открытый ключ: эфемерный X25519 → HKDF-SHA256 (соль `epk ‖ pk`,
`info = "homensai-rent/archive-secret/1"`) → ChaCha20-Poly1305, nonce 12 случайных байт (`app/archive/keys.py:179-201`);
открытие — `:222-248`. Тот же приём для ключа восстановления как получателя (`app/security/recovery.py:54-56`, `:70-84`).
Конверт лежит в комментарии ZIP (`HRKEY1`, `spec/key-envelope.md`).

**Почему.** Копии делаются по расписанию **без ввода пароля** и пароль нигде не хранится (269/270): нужна асимметрия —
шифровать открытым ключом, открывать закрытым под паролем. Устройство повторяет age (X25519-получатели, HKDF-SHA256,
ChaCha20-Poly1305) и несколько ключей restic/Borg (`app/archive/keys.py:4-13`). Смена пароля — новая пара; старые копии
несут свой `wrapped` и открываются прежним паролем. X25519 (RFC 7748) — быстрый, без проверок точки и ошибок реализации
ECDSA/ECDH на P-256; ChaCha20-Poly1305 (RFC 8439) — постоянное время без AES-NI; ключ AEAD каждый раз новый (эфемерный
обмен), поэтому случайный 96-битный nonce не повторится под одним ключом.

**Альтернативы.** RSA-OAEP — большие ключи и сложнее безопасно — **уточнить** (в коде не обсуждается); libsodium sealed box
(PyNaCl) и готовый age — нет в закреплённых зависимостях Rent — **уточнить**; HPKE (RFC 9180) — схема близка к HPKE base
mode, но не совпадает побайтно — **уточнить** переход на HPKE при версии 2 конверта; хранение пароля/секрета на ПК —
запрещено решением 270.

**Защищает от:** открытия копии без пароля/ключа восстановления; подмены секрета или ключа (теги AEAD, AAD с открытым
ключом); перебора ключа восстановления (128 бит). **Не защищает от:** вредоносной программы на ПК в момент ввода пароля;
будущего квантового компьютера («собрать сейчас — расшифровать потом»: X25519 не постквантовый) — пересмотр при
появлении в pyca/cryptography гибрида X25519 + ML-KEM (FIPS 203) — **уточнить** сроки; потери и пароля, и всех ключей
восстановления (копии не открыть — так задумано, галочки 271).

**Пересмотр:** ежегодно; внепланово — постквантовый гибрид, рекомендации BSI TR-02102-1/NIST SP 800-56A.

**Миграция:** конверт версионирован (`"v": 1`, префикс `HRKEY1`); новая схема — `HRKEY2` с чтением прежней; ключ хозяйства
меняется сменой пароля, ключи восстановления перезапечатываются на новую пару (`app/archive/runner.py:227-231`).

## 4. Поля базы: AES-256-GCM с контекстом (`v1gcm`)

**Что и где.** `app/platform/sealing.py:114-115` (префикс `v1gcm|`, nonce 12), `:244-246` (ключ = HKDF-SHA256 от
`HOMENSAI_RENT_DEV_KEY`, соль `homensai-rent/v1`, `info="gcm"`), `:249-252` (AAD), `:255-262` (запись), `:274-283` (чтение).
Поля — список `ENCRYPTED_FIELDS` (`:29-88`). Ключ проверяется при запуске: не короче 43 знаков, без шаблонов
(`:139-204`). Прежний `v0stub` (HMAC-SHA256-поток + HMAC) — только чтение (`:230-241`, `:265-302`).

**Почему.** AEAD: конфиденциальность и целостность одной операцией, AAD привязывает значение к хозяйству, таблице,
колонке и строке (`:249-252`) — перенос шифротекста в чужую строку не расшифруется. AES-GCM — NIST SP 800-38D, аппаратное
ускорение AES-NI, pyca/cryptography. HKDF даёт отдельный ключ на назначение (`:244-246`).

**Альтернативы.** `v0stub` — самодельный поток на HMAC без контекста — заменён (`app/platform/aead_migrate.py:3`);
Fernet — без AAD — **уточнить** (в коде не обсуждается); детерминированное шифрование для поиска — раскрывает равенство
значений, вместо него слепой индекс (метод 6); AES-GCM-SIV (RFC 8452, устойчив к повтору nonce) — **уточнить** при
пересмотре; vault ядра (`hfc1:`) — целевой режим при подключении к ядру (`:328-364`, `app/platform/reseal.py`).

**Защищает от:** чтения личных данных из файла базы и копии без ключа полей; переноса шифротекста между строками/полями;
незаметной правки значения. **Не защищает от:** того, у кого есть ключ полей (переменная окружения на том же ПК);
утечки длины значения; повтора nonce — случайные 96 бит под одним ключом, NIST SP 800-38D §8.3 ограничивает ~2^32 записей
на ключ — для домашней базы с запасом, счётчик записей не ведётся — **уточнить**.

**Пересмотр:** ежегодно; при подключении к ядру — формат vault.

**Миграция:** `v0stub → v1gcm` — `python -m app.ctl aead-migrate --db <база> --offline` (бэкап, перешифровка одной
транзакцией, проверка каждой записи, откат; `app/platform/aead_migrate.py:1-8`); автономный режим → vault ядра —
возобновляемый `rent-reseal/1` (`app/platform/reseal.py:1-48`). Смена ключа полей заменой переменной невозможна —
только перешифровкой (`app/platform/sealing.py:200-204`).

## 5. Контекст поля (AAD) и разделение доменов

**Что и где.** AAD полей: `"homensai-rent/v1\x00" ‖ account ‖ \x00 ‖ table ‖ \x00 ‖ column ‖ \x00 ‖ row_id`
(`app/platform/sealing.py:249-252`). AAD ключа хозяйства: `"homensai-rent/archive-identity/1" ‖ pub` (`app/archive/keys.py:43`,
`:118`); на ключ восстановления — `"homensai-rent/archive-identity-recovery/1" ‖ pub` (`:44`, `:146`); секрет копии —
`"homensai-rent/archive-secret/1"` (`:45`, `:193`). Разделители в HKDF `info` и хэшах отпечатков: `homensai-rent/archive-key`,
`chain-key`, `homensai-security/recovery-key|recovery-seal|recovery-id|rk|rs|rs-tag|login-code|webauthn-prf/…`.

**Почему.** Один ключ или шифротекст не подходит в другом месте и назначении; отпечаток одного вида не совпадает с
другим. Разделитель NUL не встречается в идентификаторах (`app/platform/sealing.py:250`).

**Не защищает от:** подмены внутри одного контекста (старое значение той же ячейки на её месте — откат) — **уточнить**,
закрывает ли это журнал-цепочка (метод 9).

**Пересмотр/миграция:** метки версионированы (`/1`); смена метки — новая версия формата и вектора.

## 6. HMAC-SHA256: слепой индекс, контрольное значение ключа, метки

**Что и где.** Слепой индекс `bi2:` — HMAC-SHA256 с ключом HKDF на хозяйство/таблицу/колонку (`app/platform/sealing.py:305-312`).
Контрольное значение ключа полей (KCV) — HMAC-SHA256 отдельным производным ключом (`:215-227`), хранится в `field_key_check`,
сравнение `hmac.compare_digest` (`app/platform/key_check.py:87`), запуск с чужим ключом запрещён (28.10-230,
`app/platform/key_check.py:124`). Метка сгенерированного пароля для перепечатки — HMAC-SHA256 ключом только в памяти
процесса (`app/archive/protection.py:158-167`). Сравнения секретов — `hmac.compare_digest`.

**Почему.** Поиск дублей и совпадений без расшифровки; разные поля и хозяйства — разные индексы; ключ индекса ≠ ключ
шифрования (`:306-309`). KCV не раскрывает ключ, а совпадение означает «тот же ключ, которым начата база».

**Альтернативы.** Простой SHA-256 значения — перебирается по словарю (РНОКПП, телефоны) — **уточнить** (в коде не
обсуждается); хранение ключа рядом с базой — нет.

**Не защищает от:** равенства значений внутри одной колонки хозяйства (индекс это и раскрывает — намеренно); перебора
короткого значения тем, у кого есть ключ полей.

**Пересмотр/миграция:** вместе с методом 4; `bi2` заменил индекс без префикса (`:315-317`), переход — та же миграция
`aead-migrate`.

## 7. Проверка пароля копий

**Что и где.** Проверка = расшифровка закрытого ключа хозяйства (`app/archive/keys.py:123-136`) плюс пробная распаковка
последней копии (`app/archive/checks.py:112-135`); 5 ошибок подряд — пауза 10 минут (`app/archive/protection.py:282-284`);
журнал проверок без пароля. Сгенерированный пароль 10–12 знаков из алфавита без похожих знаков (`secrets`,
`app/archive/protection.py:44-50`, `:92-99`); перепечатка сверяется HMAC-меткой (метод 6).

**Почему.** 270/271: пароль нигде не хранится, поэтому программа регулярно просит его вспомнить — иначе забытый пароль
обнаружится только при беде. Проверка по `wrapped` не требует носителя; пробная распаковка доказывает, что копия на носителе
открывается.

**Не защищает от:** записи пароля на бумаге рядом с ПК; перебора по украденной копии (пауза действует только в программе —
вне её защищает метод 2). Энтропия сгенерированного пароля: 12 знаков из 57 ≈ 70 бит — **уточнить** соответствие
рекомендации владельцу (в коде расчёта нет).

**Пересмотр/миграция:** вместе с методами 2 и 3.

## 8. Ключ восстановления, части Шамира, PRF

**Что и где.** Ключ — 16 байт `secrets` (`app/security/codes.py:70-71`), запись `RK1-` Crockford Base32 с 16-битной
контрольной суммой SHA-256 (`:20-31`, `:60-83`). Как получатель: закрытый X25519 = HKDF-SHA256(ключ) (`app/security/recovery.py:54-56`),
запечатывание — метод 3. Части «2 из 3» — pycryptodomex `Shamir.split(2, 3, key, ssss=False)`, GF(2^128)
(`app/security/shamir.py:22`, `:27-43`); метка набора — 16 случайных бит (`app/security/codes.py:98-106`), запись `RS1-`
с контрольной суммой (`:109-129`). Ключ из аппаратного ключа: PRF (hmac-secret) → HKDF-SHA256 → 16 байт
(`app/security/webauthn.py:60-61`, `:311-315`). До 3 бумажных и 10 аппаратных ключей (`app/archive/protection.py:71-72`).

**Почему.** 279 п. 2 (образец — несколько ключей restic/Borg) и 284: второй независимый путь к копиям; 128 бит — перебор
невозможен, поэтому растягивания нет (NIST SP 800-132 растягивает только пароли, `app/security/recovery.py:9-11`).
Crockford Base32 — без I, L, O, U, опечатка ловится до расшифровки (`app/security/codes.py:4-6`). Шамир — проверенная
библиотека, своё поле не пишется (`app/security/shamir.py:4-7`); одна часть не даёт сведений о ключе; метка из ключа
давала бы 16 бит сведений — заменена случайной (ревью DR-recovery №1, `:13-17`).

**Альтернативы.** Свой код конечного поля — запрещён (286); метка набора из ключа — отвергнута (`app/security/codes.py:101-105`);
SLIP-39 / BIP-39 (слова) — **уточнить** (в коде не обсуждается).

**Защищает от:** забытого пароля; потери одного листа с частью; опечатки при вводе; подбора ключа. **Не защищает от:**
кражи целого ключа или двух частей вместе с копией; у частей Шамира нет своей целостности — неверную часть отвергает
расшифровка (`recovery_wrong`), а не метка (`app/security/shamir.py:9-12`).

**Пересмотр:** ежегодно; длина ключа — при пересмотре NIST SP 800-63B (сейчас ≥ 112 бит для секрета без растягивания).

**Миграция:** отзыв ключа — новая пара хозяйства и перезапечатывание остальных (`app/archive/runner.py:227-231`); наборы
частей с прежней меткой читаются, предлагается перевыпуск (`app/security/shamir.py:63-73`).

## 9. Целостность: SHA-256 копии, цепочка копий (Ed25519), журнал-цепочка

**Что и где.** Манифест копии — sha256 и размер каждого файла (`app/archive/pack.py:259-270`), чтение сверяет их
(`:676-683`); контрольные итоги содержимого базы (`scripts/migrate.py:469-482`). Цепочка копий: манифест каждой копии
(номер, sha256 файла копии, `prev` = SHA-256 предыдущего подписанного манифеста) подписан Ed25519
(`app/archive/chain.py:359-373`), отпечаток ключа `HS1-` (`:178-181`), закрытый ключ — файл под DPAPI в Windows или 0600 в
Linux (`:200-231`). Журнал-цепочка: `SHA-256(prev ‖ "\n" ‖ канонический JSON)` (`app/security/integrity.py:42-44`), голова — в
подписанном манифесте копии (`app/archive/chain.py:367-370`).

**Почему.** 276: удаление, подмена или перестановка любой копии рвёт цепочку («как у биткоина», без майнинга); подпись, а не
HMAC — цепочку проверяет кто угодно **без пароля** по открытому ключу (`app/archive/chain.py:13-16`); ключ подписи
без пароля — копии подписываются по расписанию. Ed25519 (RFC 8032) — детерминированная подпись, нет риска повтора nonce
ECDSA. 273: журнал переписать вместе с базой незаметно нельзя — якорь в подписанном манифесте на носителях.

**Альтернативы.** HMAC вместо подписи — проверяющий мог бы и подделать, нужен секрет — отвергнут (по сути `:13-16`);
ECDSA P-256 — **уточнить** (в коде не обсуждается); внешняя служба отметок времени (RFC 3161) — **уточнить**.

**Защищает от:** тихого удаления/подмены/перестановки копий на носителях; правки журнала задним числом. **Не защищает от:**
злоумышленника с правами учётной записи владельца в Linux (ключ подписи лежит в открытом виде 0600 и может подписать
поддельную цепочку) — **уточнить**, нужна ли защита ключа паролем/ОС-хранилищем в Linux; от удаления **всех** копий
и манифестов на всех носителях (это видно как пропажа, но не восстановимо).

**Пересмотр:** ежегодно; SHA-256 и Ed25519 — до появления практической угрозы (постквантовые подписи ML-DSA, FIPS 204 —
**уточнить** сроки).

**Миграция:** формат `homensai-rent-chain/1`; смена ключа — предупреждение `key_changed`, цепочка продолжается новым ключом,
прежние манифесты проверяются прежним открытым ключом (`app/archive/chain.py:19-21`); новая схема подписи — новая метка формата.

## 10. Пароль входа в локальный веб

**Что и где.** `app/web/auth.py:1-17`: Argon2id (метод 2), соль 16 байт `secrets`; прежний scrypt `N=2^15, r=8, p=1`
перешифровывается при входе (`:37-40`, `:186-196`); схема базы требует `argon_m ≥ 19456, t ≥ 2`
(`migrations/webauth/0003_argon2id.sql:28`). Сессия — `secrets.token_urlsafe(32)` в cookie HttpOnly, SameSite=Strict, в базе
только SHA-256 токена (`:10`, `:329-334`); 5 ошибок — блок 15 минут, дальше вдвое до 6 часов (`:51-53`, `:269-270`).

**Почему.** 28.10-89, аудит 02.11.2026 и 279 п. 3; OWASP ASVS 5.0 V6 (пароли, список утёкших — `:99-100`).

**Альтернативы.** Без входа — было («временно без входа»), отменено (`:4`); scrypt — заменён (279).

**Защищает от:** открытия веба другим процессом/пользователем ПК без пароля; перебора онлайн (блокировка) и офлайн
(Argon2id); кражи токена из базы (только хэш). **Не защищает от:** кражи cookie из браузера владельца; кейлоггера.

**Пересмотр/миграция:** как метод 2 (`needs_rehash` при входе); поколение пароля и сессии при перешифровке не меняются.

## 11. Подпись лицензии (ядро)

**Что и где.** Ядро `homensai-platform` 4.47.0, `backend/modules/licensing/domain.py:93-95` (канонический JSON: UTF-8, ключи
по алфавиту, без пробелов, только целые), `:111-146` (Ed25519, подпись 64 байта base64 строго, ключ по `key_id`, файл
≤ 16 КиБ, повтор полей JSON — отказ). Rent передаёт только открытые ключи из `RENT_LICENSE_KEYS_FILE` (`app/platform/licensing.py:18-31`).

**Почему.** Проверка без сети, в продукте только открытый ключ; Ed25519 — короткие ключи и подписи, детерминированная
подпись. Обоснование выбора в ядре — **уточнить** в документации ядра (в Rent его нет).

**Защищает от:** подделки и правки файла лицензии. **Не защищает от:** правки самой программы (проверка локальная);
кражи закрытого ключа издателя (вне продукта).

**Пересмотр/миграция:** вместе с ядром; ротация ключей — несколько `key_id` в файле открытых ключей.

## 12. Второй фактор и восстановление входа

- **TOTP** (Google Authenticator) — RFC 6238 поверх RFC 4226, SHA-1, 6 цифр, 30 с, секрет 20 байт; именно эти параметры
  понимают все приложения (`app/security/totp.py:1-11`, `:26-29`); повтор уже принятого шага запрещён. SHA-1 в HMAC не
  страдает от коллизий SHA-1. Для копий не используется — ничего не расшифровывает (269/282).
- **WebAuthn L3** — проверка по разделам 7.1/7.2 спецификации своими силами поверх pyca/cryptography (ES256, EdDSA, RS256),
  потому что проверенного пакета WebAuthn в зависимостях нет (`app/security/webauthn.py:1-6`, `:45-48`); счётчик подписей
  против клонов. **Уточнить** при пересмотре: переход на закреплённую библиотеку (py_webauthn/fido2).
- **Коды восстановления входа** — 10 кодов по 125 бит, хранится SHA-256 с доменом и номером набора: при энтропии ≥ 112 бит
  NIST SP 800-63B §5.1.2.2 допускает быструю одностороннюю функцию (`app/security/login_codes.py:1-10`, `:56-58`).

**Пересмотр:** ежегодно и при новой редакции W3C WebAuthn / NIST SP 800-63B.

## Что пометить «уточнить» — сводка

1. Плановый срок пересмотра «ежегодно» — предложение документа, утвердить владельцу.
2. Пароль копий без NFKC-нормализации, пароль входа и PIN — с NFKC (разное поведение).
3. Нет автоматического усиления параметров `wrapped` при успешной проверке пароля копий.
4. Целевое время Argon2id на ПК владельца и стоимость перебора PIN по копии — нет замера.
5. Режим `env` (PBKDF2-SHA1 × 1000 формата ZIP): сроки вывода из употребления.
6. Постквантовый переход: гибрид X25519 + ML-KEM для конверта, ML-DSA для цепочки — когда.
7. Переход конверта на HPKE (RFC 9180) при версии 2.
8. AES-GCM: счётчик записей на ключ полей не ведётся; AES-GCM-SIV как альтернатива.
9. Защита ключа подписи цепочки в Linux (сейчас файл 0600 без шифрования).
10. Откат значения ячейки внутри того же контекста AAD — закрывает ли журнал-цепочка.
11. Энтропия сгенерированного пароля копий (≈ 70 бит) — достаточно ли.
12. WebAuthn: переход на проверенную библиотеку; кодировка соли PRF в запросе браузера.
13. Альтернативы без обоснования в коде: 7z, age/GPG-контейнер, PBKDF2/bcrypt, RSA-OAEP, libsodium, Fernet, SLIP-39,
    ECDSA, RFC 3161 — сравнение не записано в коде и решениях.
14. Обоснование подписи лицензии — в документации ядра.
15. Формат vault ядра (`hfc1:`/`bi1:`) и служебного бэкапа — вне этого выпуска спецификации.
